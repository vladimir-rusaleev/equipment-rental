# Rent — прокат строительного инструмента

Сервис для одного пункта проката. Клиент выбирает инструменты и даты, собирает
корзину и оформляет бронирование. Сотрудники управляют оборудованием, выдают
инструменты и принимают возвраты через отдельную панель.

Проект состоит из четырёх микросервисов на Go и веб-интерфейса.

## Возможности

- Каталог с поиском, категориями и календарём доступности.
- Корзина с отдельным периодом аренды для каждой позиции.
- Бронирование всего комплекта с защитой от пересечения резервов.
- Регистрация, авторизация и личный кабинет с историей заказов.
- Выдача, частичный возврат и отмена бронирований.
- Управление моделями, тарифами, экземплярами и их техническим состоянием.
- Роли клиента, сотрудника и администратора.
- Повтор незавершённых операций и очередь уведомлений.

**Стек:** Go, PostgreSQL, gRPC/Protobuf, HTTP/JSON, HTML/CSS/JavaScript, Docker Compose.
Данные сохраняются в PostgreSQL; для тестов доступен memory-режим. Уведомления выводятся в лог.

## Быстрый запуск

Для локального запуска нужны Go 1.27.1+ и Docker Compose для PostgreSQL.

```bash
cp .env.example .env
```

Задайте в `.env`:

| Переменная | Назначение |
|---|---|
| `SERVICE_KEY` | Общий ключ внутренних вызовов, минимум 16 символов |
| `ADMIN_EMAIL` | Почта первоначального администратора |
| `ADMIN_PASSWORD` | Его пароль, от 10 до 72 байт |
| `STORAGE` | `postgres` (в `.env.example`) или `memory` |
| `POSTGRES_PASSWORD` | Пароль владельца PostgreSQL |
| `APP_DB_PASSWORD` | Пароль отдельных пользователей сервисов |
| `POSTGRES_PORT` | Порт локального PostgreSQL, по умолчанию `5432` |

```bash
make db-up  # PostgreSQL в Docker, с постоянным томом
make run    # сервисы локально
```

Откройте [localhost:8080](http://localhost:8080/). Для входа администратором
используйте данные из `.env`; клиент может зарегистрироваться через интерфейс.

При первом запуске создаются две демонстрационные модели по три экземпляра.
Повторный запуск не дублирует каталог и не сбрасывает пароль администратора.
Чтобы начать с пустого каталога, задайте `SEED_DEMO=false` в `.env`.
Frontend встроен в Gateway: отдельный Node-сервер и npm-пакеты не нужны.
Остановка — Ctrl+C; после изменения исходников повторите `make run`.

В WSL при проблемах со snap-обёрткой Go можно указать бинарник напрямую:

```bash
make run GO=/snap/go/current/bin/go
```

### Docker Compose

После настройки `.env`:

```bash
docker compose up --build
```

Снаружи доступен только Gateway на `127.0.0.1:8080`; gRPC-сервисы находятся
во внутренней сети Compose.

**Данные сохраняются в томе `postgres-data` и остаются после перезапуска.**
`docker compose down` сохраняет том; добавление `-v` удаляет его вместе с данными.
Без БД можно запустить `make run-memory` — в этом режиме данные временные.

## Архитектура

```text
Браузер / Frontend
        |
        | HTTP / JSON
        v
     Gateway
        |
        +--- gRPC ---> Rental --- gRPC ---> Inventory
        |                |
        |                +--- Outbox worker --- gRPC ---> Notifier
        |
        +--- gRPC -------------------------> Inventory
```

Outbox worker выполняется внутри Rental. Оба пути к Inventory ведут
в один сервис: Gateway запрашивает каталог, Rental управляет резервами.

| Сервис | Ответственность |
|---|---|
| **Gateway** | HTTP API, проверка токена, преобразование запросов и вызовы gRPC |
| **Rental** | Пользователи, роли, корзины, заказы и продолжение незавершённых операций |
| **Inventory** | Каталог, физические экземпляры, доступность, резервы, выдача и возврат |
| **Notifier** | Приём уведомлений, дедупликация и доставка через адаптер |

У Rental, Inventory и Notifier отдельные базы и пользователи PostgreSQL.
SQL-миграции встроены в бинарники и применяются автоматически при старте.

Внутри сервисов разделены controller, usecase, repository и adapter.
Интерфейсы зависимостей объявлены у потребителя, сборка выполняется в `internal/app`.
В Rental отдельные usecase пользователей, корзины и заказов; периодические задачи
вынесены в worker-пакеты. В Gateway маршруты переводятся в gRPC-вызовы через `switch`.

Оформление сначала создаёт заказ `pending`, затем Inventory атомарно резервирует
весь комплект, а Rental подтверждает заказ. При потере ответа операция повторяется
с тем же идентификатором. Уведомление записывается вместе с изменением заказа
и передаётся отдельным обработчиком.

## Основные правила

- Клиент выбирает модель и количество, Inventory назначает конкретные экземпляры.
- Корзина не резервирует оборудование; доступность проверяется при оформлении.
- У каждой позиции свои даты. Весь комплект бронируется либо целиком, либо никак.
- Период `[start, end)`: 10–12 ноября — двое суток, дата возврата не оплачивается.
- Цена — тариф × количество × дни. Согласованный тариф сохраняется в заказе.
- Повтор checkout с тем же `request_id` возвращает тот же заказ.
- До выдачи бронь можно отменить. Выдача выполняется для заказа целиком,
  возврат — в том числе по отдельным экземплярам.

Клиент видит свои заказы. Сотрудник работает со всеми заказами, выдачей,
возвратами и экземплярами. Администратор дополнительно управляет каталогом,
тарифами и ролями. При отмене чужой брони обязательна причина.

## Структура проекта

```text
frontend/             HTML, CSS, JavaScript и встраивание файлов в Gateway
gateway/              внешний HTTP API и адаптер gRPC
rental/               пользователи, корзины, заказы, outbox и workers
inventory/            оборудование, доступность и резервирование
notifier/             очередь и доставка уведомлений
internal/platform/    общие технические средства
internal/postgres/    подключение и запуск миграций
docker/postgres/      создание баз и пользователей
api/rent/v1/          Protobuf-контракты
pkg/generated/        сгенерированный Go-код
scripts/              локальный запуск и сквозная проверка
docs/                 подробная документация
```

В репозитории один Go-модуль; сервисы собираются в отдельные бинарники и контейнеры.

## Проверки и генерация

```bash
make build      # собрать четыре сервиса
make test       # Go-тесты с детектором гонок
make smoke      # сквозной тест в памяти; нужен Python 3
make test-postgres # отдельная тестовая БД в Docker и проверки с перезапуском
make generate   # обновить Protobuf-код; нужны protoc и Go-плагины
```

Проверяются конкурентное бронирование, атомарность комплекта, повтор запросов,
права доступа, разные даты позиций, частичный возврат и обработка сбоев.
Smoke-тест запускает сервисы на временных портах и останавливает их после проверки.

Сгенерированный код включён в репозиторий: для обычной сборки protoc не требуется.
При изменении `.proto` обновляйте и коммитьте сгенерированные файлы вместе с контрактом.

## Текущие ограничения

Рекомендуется по одному экземпляру каждого сервиса: распределённые аренды задач
доставки уведомлений пока не реализованы. Уведомления идут в лог; онлайн-оплата,
продление, залоги и доставка не реализованы. Данные старого memory-режима
автоматически в PostgreSQL не переносятся.
