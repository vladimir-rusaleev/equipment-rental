# PostgreSQL

## Запуск

```bash
cp .env.example .env  # только если .env ещё нет; существующий не перезаписывайте
# Настройте SERVICE_KEY, ADMIN_EMAIL, ADMIN_PASSWORD и пароли БД.
make db-up
make run
```

Либо весь стек в контейнерах:

```bash
docker compose up --build
```

В PostgreSQL создаются отдельные базы `rent_rental`, `rent_inventory`, `rent_notifier`
и одноимённые роли. Сервисы не используют владельца кластера `rent_owner` и не имеют
доступа к базам друг друга. Начальную настройку выполняет `docker/postgres/init-db.sh`.

Локально используется `127.0.0.1:${POSTGRES_PORT}`, в Compose — `postgres:5432`.
Данные находятся в именованном томе `postgres-data`. Обычный `docker compose down`
его не удаляет. `docker compose down -v` удаляет данные.

Переменные `.env`:

- `STORAGE=postgres` — постоянное хранилище; `memory` — временное.
- `POSTGRES_PASSWORD` — пароль владельца кластера, используется при инициализации.
- `APP_DB_PASSWORD` — пароль ролей сервисов, используется при инициализации.
- `POSTGRES_PORT=5432` — опубликованный порт локальной БД.
- `POSTGRES_HOST` — необязательно; по умолчанию `127.0.0.1`.
- `POSTGRES_SSLMODE` — необязательно; локально `disable`.

При внешнем PostgreSQL вместо этих настроек можно задать отдельные
`RENTAL_DATABASE_URL`, `INVENTORY_DATABASE_URL`, `NOTIFIER_DATABASE_URL`.
Укажите `STORAGE=postgres`. Не добавляйте реальные пароли и URL с ними в Git.

Переменные инициализации PostgreSQL действуют только при создании пустого тома.
Изменение пароля в `.env` не меняет пароль уже существующей роли: его необходимо
изменить в PostgreSQL и затем обновить конфигурацию приложений.

Существующий `.env` проекта дополнен настройками БД без изменения данных администратора.
Первая БД создаётся пустой; старые данные в памяти автоматически не переносятся.

## Миграции и таблицы

Миграции находятся в `<service>/internal/repository/postgres/migrations/` и встраиваются
в бинарники. При старте применяются по порядку одной транзакцией под advisory lock.
Таблица `schema_migrations` хранит имена и контрольные суммы. Применённый файл нельзя
редактировать: для изменения схемы создавайте следующий SQL-файл.

| Сервис | Таблицы |
|---|---|
| Rental | users, sessions, carts, orders, outbox |
| Inventory | models, units, reservations, reservation_items, allocations, seed_history |
| Notifier | notifications |

У заказов индексируются пользователь, ключ запроса и состояние; содержимое заказа
с историей и сохранёнными ценами хранится как JSONB-снимок. Корзины также хранятся
в JSONB. Резервы и физические назначения нормализованы для проверки интервалов в SQL.

Inventory использует расширение `btree_gist`, входящее в образ PostgreSQL.
Роль Inventory должна иметь право установить это trusted-расширение в своей базе.

## Гарантии

- Резервирование комплекта выполняется одной транзакцией. Модели блокируются
  `FOR UPDATE` в одном порядке, повторные операции сериализуются по ID заказа.
- Ограничение `EXCLUDE USING gist` запрещает пересечение `daterange` для одного
  экземпляра, даже при записи в обход приложения. При отмене резерв освобождается.
- Назначения уже завершённой аренды сохраняют исторический интервал. Ранний возврат
  пока не освобождает оставшуюся часть срока.
- Запись заказа, outbox и очистка прежней версии корзины атомарны. Устаревшая версия
  заказа не может перезаписать новую.
- Сессии, промежуточные операции, outbox и история дедупликации переживают перезапуск.
- Демокаталог создаётся один раз. Повторный старт не восстанавливает старые тарифы
  и не добавляет экземпляры заново. Bootstrap администратора не сбрасывает пароль.

Рекомендуется по одному экземпляру каждого сервиса. Lease-механизм для нескольких
параллельных обработчиков уведомлений пока не реализован; внешняя доставка допускает
повторы при неоднозначном сбое. Подтверждённые брони сами по времени не истекают.

## Проверки

```bash
make test             # memory-тесты; PostgreSQL-тесты без URL пропускаются
make smoke            # HTTP/gRPC-сценарии в memory-режиме
make test-postgres    # отдельный временный PostgreSQL в Docker
```

`test-postgres` создаёт изолированный Compose-проект со случайным портом и временной
БД в tmpfs. Он не использует вашу рабочую БД и удаляет тестовый контейнер после проверки.
Go-тесты проверяют конкурирующие резервы через разные подключения, SQL-ограничение
пересечений, откат комплекта/заказа, версии, сессии, outbox и дедупликацию.
Сквозной тест перезапускает приложения и проверяет сохранность состояния и продолжение
незавершённого бронирования.

Для своей одноразовой тестовой БД задайте `RENTAL_TEST_DATABASE_URL`,
`INVENTORY_TEST_DATABASE_URL`, `NOTIFIER_TEST_DATABASE_URL` и выполните `make test`.
Эти тесты создают записи: URL должны вести в тестовые, а не рабочие базы.
